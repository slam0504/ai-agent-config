## 詞表:代理人速記 → 自然中文(2026-08-19 新增)

模型在長對話中自我增強出的內部速記。一對一長期對話裡讀者或許能根據前後文理解,
但團隊文件的每位新讀者都得重新理解,必須避免。
修法多半是「展開成完整句子」,不是逐詞替換——同一速記在不同語境展開成不同句子,
機械代換會產出同樣不自然的重複套語。

### 一律改寫(生造中文速記,內外都不用)

| 速記 | 展開方向 | 說明 |

## 構詞模式(比詞條更通用,新速記出現時先對照這裡)

1. 「零+名詞」壓縮(零丟失 / 零接線 / 零變更)→ 展開成否定句
2. 「異 / 全 / 雙 / 逐+名詞」文言壓縮(異 cwd / 全 package / 逐 task)→ 展開(cwd 不一致時 / 所有 package / 逐項任務)
3. 英文名詞硬接中文動詞(打通 wire / 收乾事件 / 錄流收尾)→ 拆成完整動作句
4. 名詞堆疊無動詞(收尾 ownership / Usage 語意雙軌 / STALE 權威判定)→ 補主詞與動詞
5. 顏色與攻防隱喻(打紅 / 紅燈特徵 / 帶紅)→ 直述「測試失敗」;「偽陽性」通行可留
6. 保留英文的術語首次出現加中文說明,之後可直接使用

## 內外分界

僅供代理人使用的內部紀錄(例如 `.agent/`、`.remember/` 與內部進度紀錄)可保留
精確英文術語及既有縮寫。提交至 README、docs、commit、PR 或交付給使用者的內容,
仍須遵守本規範。內部紀錄的內容要進對外文字時,經過語言校對那一段,不直接複製貼上。

## 校對工作流(v2:兩段式)

輸出書面中文分兩段檢查,不得合併為一次:

1. **技術審查** — 事實、程式路徑、測試證據。此段不管語言。
2. **語言審查** — 只處理台灣用語、句子完整性與可讀性;**不得改變技術判定**。
   - 對岸用語:環境有 `zhtw-mcp` 之類工具先跑 lint 列 issue
   - 代理人速記:grep 清單掃(`守門|打紅|帶紅|零接線|閉環|收乾|打通|錄流|量牆鐘|臨場|誠實邊界`)
   - 句子自然度:無法機械判定,人工或獨立語言 reviewer 通讀

lint issue 分四類:必改 / 建議改 / false positive(語境誤判,如「一次性 → 拋棄式」、
「前綴 → 字首」、「通過[pass 意] → 透過」)/ 排版破壞(標點空格刪除、`-` → `~` 數字範圍、
表格半形 `,` 改全形)。確定需修改的項目可批次替換;邊界案例依既有用詞或使用者偏好處理;
false positive 與排版類絕不動。完成後使用者肉眼掃補抓字典盲區。

全文詞彙替換前先 grep 既有用詞,對齊目前最常使用的版本,避免引入新詞造成不統一。
不確定某詞是否台灣常用時,主動標出讓使用者選、不要默默用下去。

## 語感避免類(v1 保留)

- 「動詞+爆」構詞(拉爆 / 打爆 / 捅爆 / 刷爆)— 對岸網路語感
- 帶政治梗的流行語(開好開滿 / 發大財 / 貨出得去)— 技術文件會觸發政治聯想
- 中性網路語(一坨 / 超猛 / 神扯 / 爆炸)— 閒聊可用,正式書面避免

**核心原則(使用者明示)**:台灣中文語境沒有合適對應詞時,直接用英文原文並
附註說明,不要生造中文譯名。

**Why**:共同語言降低溝通摩擦。對岸用語與生造譯名觸發違和感;代理人速記則來自
模型的脈絡自我增強——一旦某速記在對話早期出現,後續生成傾向沿用並加深它,
單靠「請用自然中文」的指示每次都要對抗整個上文累積的慣性,所以需要迴圈外的
固定語言審查段作為打斷點。

**How to apply**:輸出任何書面中文前對照本表與構詞模式;技術內容完成後跑第二段
語言審查。遇到新的技術詞彙先判斷台灣是否有慣用譯名,沒有就用原文加一句說明。
使用者再校正新詞或新句時,更新本表。
